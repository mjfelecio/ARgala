# ARgala agent operating manual

ARgala is an Android-only travel discovery app built with Expo SDK 57 and strict TypeScript. It combines Google-powered discovery around arbitrary coordinates, walking route display, and existing GPS/compass camera overlays. The approved ACLC blueprint adds selected-featured-destination Viro/ARCore local tracking, beginning with a development-only native feasibility checkpoint. Prioritize mobile performance and Android-supported APIs. This supersedes the earlier blanket exclusion of ARCore; it does not authorize geospatial anchors, object recognition or AR navigation.

## Architecture and data boundaries

- Keep feature code in `src/features/`; route files only assemble screens. Screens consume typed services; Google-specific request/response mapping stays behind provider boundaries. Pure geographic calculations must not import device APIs.
- Preserve provider identifiers unchanged. Base identifier length checks on documented provider constraints or shared application payload budgets; enforce complete request limits before quota consumption or provider work.
- First-launch Welcome uses `argala.onboarding.v1`; only `complete` commits onboarding. Store `pending` before saving preferences so partial completion cannot become a legacy-install bypass after restart. Language previews stay local until Continue; preserve the existing activation radius, bypass restored sessions and never rewrite legacy preferences during migration.
- Use React context for authentication/preferences, TanStack Query for transient server state, and UniWind (Tailwind CSS v4) for presentation with HeroUI Native as the primary component library. `global.css` owns design tokens and semantic/component themes; do not duplicate them in a TypeScript theme. Use React Native `StyleSheet` only for dynamic native requirements, animation or third-party constraints. Reuse suitable HeroUI components before custom primitives; UniWind is distinct from NativeWind. See [UI infrastructure](docs/ui-infrastructure.md).
- Google Places and Routes web-service calls must go through authenticated Supabase Edge Functions. Keep server credentials in Edge secrets. The public Android Maps SDK key belongs in native configuration with package/SHA restrictions; it is distinct from server keys.
- Preserve Edge authentication, schema validation, payload/result/radius limits, field masks, timeouts, sanitized errors and the atomic PostgreSQL request limiter before paid provider calls. See backend setup for deployment details.
- Do not persist provider results to disk or add POI/location-history/camera-frame storage. Clear transient query data on authentication changes. Display provider attributions and walking warnings with the relevant content.
- Use `setPlaceSelection` for transient POI navigation handoffs. Configure retention before storing an unobserved query; the default zero cache lifetime can otherwise evict a summary before its destination screen mounts. Cache presence grants no paid-request authority.
- Nearby and Details currently share the Google adapter's complete field mask. Reuse normalized discovery fields only with known matching response language, including destination-nearby handoffs; missing optional fields do not justify another paid request. Bound reuse by the source response's `dataUpdatedAt`, preserving it when seeding Details; observation and navigation must not renew the reuse window. Keep this completeness rule aligned with the backend mask when adding fields. Unknown summaries and expired results retain explicit recovery.
- Featured Destinations owns the provisional D01–D09 catalog and per-field approval evidence. Keep destination centers separate from accessible route entrances, use only approved bundled preview media, and never forward curated identifiers into Google details or Home's Google selection path. Its fixed 500 m nearby radius is independent from general discovery and local AR activation. See [destination content readiness](docs/design/clean-explorer/DESTINATIONS.md).
- Run location/heading watchers and camera preview only while focused and foregrounded; clean up asynchronous subscriptions even if setup finishes after unmount. Track continuous watcher health separately from the last valid position. A one-shot fix cannot clear a watcher failure or refresh the continuous watcher's sample age. Consumers that enforce freshness must track watcher sample time separately from the latest position.
- Keep high-frequency sensor state below the native camera's rendering boundary. Use an independent expiry clock and the sensor event's application receipt time for pure rendering; receipt time never replaces native position/watcher sample age or heading quality. Compass-only updates must not recalculate geographic distances or activation eligibility. AR labels use display-only horizontal stops with a boundary buffer instead of continuously chasing sensor noise; invalid/stale direction still removes labels immediately, and raw coordinates determine proximity and paid-request origins. Reset display placement on geometry changes or reacquisition; do not widen raw FOV or eligibility to retain a label.
- The compact degree readout uses display-only circular 10° stops with an 8° hold threshold. Keep its state inside the header; raw validated heading still drives POI projection. Invalid/stale direction must clear the readout immediately and reacquisition starts fresh.
- Read foreground state through the shared subscription-consistent snapshot; a screen must not require another background/foreground event to start its sensors. Bound the complete focused location startup, including permission and service checks, and retire timed-out attempts so late native results cannot restart them.
- Check existing permissions before requesting them. Native permission activities can background the app; share in-flight permission work across foreground owners and never treat resume as permission to prompt again. After denial, a new prompt requires an explicit Retry. Recheck grants on resume so revocations take effect; do not cache settled grants.
- Keep separate concepts separate: nearby discovery defaults to **1000 m**; AR activation defaults to **100 m** for all POIs and is a device-local preference; the destination-centered establishment radius is fixed at **500 m** for the catalog feature. Device-local activation is not a centrally managed setting for all users. Limits live in `src/config/limits.ts` and shared server contracts.
- Paid Places/details/routes requests require an explicit user action: Search, POI selection or Walk. Mounting, refocusing, foreground return, language changes and query invalidation must not silently initiate paid requests. Discovery starts with Search. Any future movement-triggered refresh needs a deliberate distance/cost policy. Expansion is local; hide details-recovery actions when a complete response is already present, while retaining explicit recovery for missing, failed or evicted details.
- Dead preview links must not start permission work or location watchers; enable sensors only for a claimed preview session that needs them. Walking preview acquisition requires a single-use transient user intent and a fresh current foreground GPS/watcher sample. A disabled session observer may reuse a result across remounts but must never inherit request authority; retry must be explicit. Keep the submitted route origin/destination separate from the moving user marker and later POI metadata, and reuse matching completed preview snapshots without a new provider call. Home, Details and AR use the dedicated Directions screen; Home must not calculate a separate route.
- Walking navigation starts explicitly and consumes the existing foreground preview location owner/expiry clock. Preserve immutable original route and captured destination; local Turf progress and display geometry never authorize a provider request. Keep original fit geometry separate from the trimmed polyline so GPS updates cannot refit the camera. Progress requires fresh continuous-watcher samples with stricter walking accuracy, ambiguity/jump guards and corroborated acquisition/off-route/arrival; uncertain progress is historical, and Stop restores the complete route. Do not snap the native user marker, record location history or add automatic rerouting/background navigation.
- Never fabricate tourist descriptions or verified preview assets.
- Destination Viro AR must keep pending entry/startup separate from an established live session. Fresh selected-destination eligibility is required immediately before its first scene mount; outside-radius continuation and the provisional five-minute restoration grace begin only after first tracking-ready. Interrupted/failed initial startup needs fresh eligibility. Already-live recovery does not require continuous GPS enforcement. Keep permission/install-attempt ownership outside disposable native views; system-activity resume cannot automatically recreate an installation prompt, and decline/failure requires explicit Retry.
- Within a surviving Viro native coordinate frame, temporary tracking loss retains the captured orientation and focused panel transform. NORMAL recovery must not recenter. Rebase only on explicit Recenter or a new/reset native frame. Do not mount Expo Camera alongside Viro or feed per-frame pose into navigation/root React state.
- Viro logical ownership includes admission ID, selected destination, principal and provenance together. Changing any invalidates restoration. Resolve lazy native scene code before final fresh-entry authorization; code loading cannot turn an old check into authority. Equivalent callback rerenders must not retire foreground ownership or repeat interruption handling; keep ownership effects stable while reading the latest committed lifecycle callbacks.
- Bound Viro suspension grace with wall and independent process-elapsed deadlines; a partial wall-clock rollback cannot extend it. Late expiry callbacks cannot invalidate a recovered live frame. Tracking loss retains the frame until normal recovery or an explicit tracking Retry; that Retry preserves logical progress/live admission but must not create an automatic install-prompt loop after interruption.
- In Viro panels, decorative text/backplates and disabled surfaces must explicitly ignore event handling; absence of a callback does not make native geometry pass through hits. Use accurate geometry hit tests on the visible control quad with one completed-click owner. Rotated axis-aligned background bounds can otherwise intercept controls. Keep explicit background-before-glyph rendering order for translucent panel layers; text bitmap quads write depth in the pinned renderer. Device verification remains required for hit behavior and alpha artifacts.

- Keep Android `MapView.userInterfaceStyle` unset: the explicit light override crashes the tested Fabric build during native initial-prop conversion. Use the native default plus the shared CSS-derived custom map style; screen-level mocks do not verify native enum serialization.
- A retained native map must disable `showsUserLocation` when its screen loses focus/foreground ownership or is waiting for a current location. Stopping the Expo watcher alone does not stop Google Maps' separate high-accuracy location source. Preserve the map instance and camera while releasing that native source.
- The version-checked Android Maps patch maps the default `system` style to `MapColorScheme.LIGHT` for the approved light-only UI. React Native's app-level Appearance override does not change the tested Google renderer's system-following color scheme. Verify native map colors on a rebuilt APK under a dark OS theme.
- For map docks, measure the full scene separately from the native map. Map height is the scene minus the shared collapsed peek plus shared corner coverage, capped to the scene, and never depends on expanded occupation. Credits and floating controls follow current occupation; native bottom padding reserves overlap above the collapsed baseline including corner coverage. Explicit Fit uses settled geometry; automatic route fitting is limited to a new route or actual layout change, never sheet transitions or refocus. The version-checked Android Maps patch applies credits padding without restoring an old camera target; padding must not pan or zoom map content. Preserve the current snap index when viewport/header dimensions change; native callbacks may not fire again for the same index. Layout measurements and provider readiness are separate signals: omit native map padding until the current map instance fires `onMapReady`, and reset readiness when that instance is remounted.
- Temporary M1 decision (2026-10-25): guide users to use the finger pad to hold the square briefly, then release. Short taps are unreliable in pinned Viro 3.0.3 and remain an accepted platform limitation for this prototype. The owner deferred native correction and accepted held interaction as passable; do not add a native tap patch or claim short-tap reliability. Keep one completed-click owner for the square’s text, fill and border.
- Bound Viro utility overlays to their visible controls/content and keep `pointerEvents="box-none"`; a transparent full-screen wrapper is not proof that native touches will pass through. Keep native scene bounds independent of chrome and repeat touch delivery on the physical device; mocked handlers do not establish native hit routing.
- Keep the AR camera in the measured full-screen scene, outside the safe-area overlay layout. Native camera bounds must never depend on sheet occupation, header or attribution height; retain positive bounds across refocus and continue unmounting the camera on blur/background. When the parent native stack reveals AR, wait for its opening `transitionEnd` before restarting the preview; focus alone returns before the scene finishes appearing and can leave CameraX's inner crop transform unapplied.
- Android camera preview uses CameraX's transform-compatible TextureView mode through a version-checked dependency patch. Build `expo-camera` from source; its precompiled artifact bypasses Kotlin changes. Full React bounds alone do not verify the native preview's aspect ratio after stack navigation.
- Expo Router 57.0.29's initial-link notification is patched to run after commit with cleanup for pending URLs. Keep initial URL parsing synchronous where supported, preserve live links, and never notify React state from a startup render that may suspend or be abandoned. The dependency patch runner verifies this JavaScript patch alongside the native patches.
- For AR camera docks, carry requested expansion through the controlled native sheet index; an imperative snap may be discarded before native layout readiness. Preserve logical expansion separately from the index clamped to a one-detent viewport. Keep controlled index updates on a layout-aware native path; configurations that write shared values during React render are invalid (Gorhom 5.2.14 requires `animateOnMount` for this AR flow).
- Keep the authenticated JavaScript tab bar in normal layout below the map scene; the navigator owns its bottom inset. Preserve the map instance, selection and route through focus-driven GPS restarts, but require current device location for device-centered searches, the native user marker, Recenter, route origins and arrival. A known viewport or selected destination remains browsable without GPS; explicit text/area search, Details recovery and external destination navigation do not grant physical location authority. Interactive maps extend behind the status bar; inset floating controls instead, use the shared CSS-derived light Google style, and release screen status-bar styling on blur. Explore owns a branded floating search bar, without a duplicate navigator header or top Settings action; Profile owns settings. The legacy generic AR route is dormant and starts no sensors; selected-destination native AR belongs on the parent stack and provides an explicit return to Explore. Settings stays on the parent stack so Back restores the originating tab. See [app shell navigation](docs/app-shell-navigation.md).

## Selected-destination AR admission

- Admission is principal-scoped and source-lease fenced. URLs, cache presence and remote map centers grant no geographic authority. Transfer handles are single-use; pending real entry revalidates the selected destination before first native mount and first tracking-ready.
- Stop initial-entry GPS only after tracking-ready establishes the live session. Established recovery retains its bounded exemption; expired logical sessions are terminal and return to Explore for a fresh handoff rather than retrying the retired admission.
- Simulation is an explicit development-only path, never synthetic samples injected into the real GPS owner. Draft ACLC content is restricted to `pilot-aclc`; preserve destination identity and development provenance through every transfer/loader/mount gate.

## Internationalization and error contracts

- Keep all app-owned display copy in `src/i18n/locales/`: labels, validation, alerts, loading/empty states, permission guidance, success messages, errors and fallbacks. Partial Korean/Japanese translations may fall back to English through i18next. Product/proper names, language autonyms and provider-attributed content may remain data values.
- Services and native/provider adapters preserve stable error codes. Map recognized failures to feature-owned codes or keys; account for both rejected setup promises and later error callbacks. Use SDK error types/codes rather than parsing English message text.
- Translate at the UI boundary. Raw native, SDK and server `error.message` values are diagnostic data and must never become display copy, including in generic fallbacks. Unknown failures use a feature fallback such as `location.unavailable`, `service.failed` or `auth.failed`.
- Keep message keys or error codes in state and call `t()` during rendering so visible messages follow language changes. New or changed error paths need English, Korean and Japanese resources for their known cases and generic fallback.
- Follow the existing error contracts in [location](src/features/location/errors.ts), [Edge requests](src/lib/edge-error.ts) and [authentication](src/features/auth/errors.ts). Extend the relevant contract when adding failure cases.

## Development and Git workflow

- Ask the owner before starting each development or preview APK build, including EAS builds. Approval for an earlier build or a general implementation/performance task does not authorize another build. Prepare and verify the concrete changes first, then request approval for the specific APK. Batch planned feature work before consuming EAS build quota.
- When routine product or implementation choices are delegated, prefer the simpler, stable option over a more complex feature-complete approach. Preserve correctness and fail clearly when confidence is insufficient. Keep low-battery device tests brief; continue offline checks if the phone powers off and record the resulting verification limits.
- Make small, reviewable changes with a clear success criterion. Inspect the relevant flow and current documentation before editing; avoid unrelated refactors or new libraries just to imitate another project's stack.
- Add focused regression coverage for behavioral fixes. Exercise the real hook/screen/service while mocking native or network boundaries; demonstrate the reported failure before the fix.
- Lifecycle regressions must exercise the installed SDK's focus hooks and delayed navigation readiness when those gates affect startup. Replacing a focus hook with a plain effect can hide a screen that never starts its sensors or deadline. Keep development diagnostics free of coordinates, credentials and raw native errors.
- Verify review findings against code and behavior. When a finding exposes a shared failure pattern, inspect sibling producers and UI consumers and fix confirmed instances together. Record lasting architecture rules here; keep feature details in code and tests.
- Validate each coherent change before committing. Use Conventional Commit subjects; include a concise body when motivation or material behavior needs explanation. Preserve incremental history and never merge a PR unless asked.
- Report exactly which checks ran and what remains unverified. Update validation evidence when behavior or coverage changes. Keep credentials and local environment files out of Git.

## Verification

Run lint and typecheck before declaring any task done. `npm run check` runs both plus the Vitest suite. Run targeted regressions during development, then the full check for the completed change.

Localization regressions must exercise actual locale resources and the real error-to-UI path, covering known errors, unknown fallbacks, recovery and language changes where relevant. Use actual SDK error classes when their shape affects mapping. Query lifecycle/cost tests must use the defaults from `src/lib/query.ts` and cover refocus, foreground return, remount and failure recovery; an infinitely fresh test cache can hide repeated paid calls.

For Edge changes, also run `npm run check:edge` and `npm run lint:edge`; run `npm run test:limiter` when limiter behavior or migrations change. For native configuration or SDK changes, run `npx expo install --check`, `npx expo-doctor`, `npm run check:android` and `npm run export:android`. The PR workflow repeats these checks, including the isolated PostgreSQL test.

Typechecks, mocked component tests, configuration introspection and Metro/Hermes exports are distinct from an APK build or physical-device verification. Never claim working GPS, compass, camera, Maps or live Google/Supabase integration without actually testing them. Before client demonstration/UAT, build and install a real Android APK with configured providers and field-test permissions, maps, GPS, camera, headings and routes. Record the device, configuration, scenarios and results.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

## Local guest travel journal

- Guest access is an explicit durable local mode after onboarding, not a Supabase session. Wait for the committed guest route guard before navigation. Keep the journal inside the app shell so changing its principal cannot remount the sign-in transition. Edge authentication and paid-request authority remain unchanged; guests must sign in for online Places/routes.
- Persist only curated destination IDs, Google Place IDs and earned visit times in the journal. Never persist provider display content or coordinates with a bookmark. Reopening an identifier cannot silently spend provider quota.
- Serialize journal writes and guest merges. Check the current owner after reads immediately before claiming the first account write. Once claimed while current, finish that serialized transfer for its captured account even after sign-out; later accounts do not inherit an already-claimed guest transfer. Persist the account result before clearing the guest source; failed reads/writes retain their data, disable unsafe edits and expose localized recovery. Account keys and in-memory owners must change with the actual principal; late completions cannot update a different account's UI.
- Award Passport progress only after the first tracking-ready event of an approved, verified, non-simulated destination entry for the current principal. Capture the earned event only in the tracking-ready callback; a retry may replay that captured event but cannot create one from a shared bookmark error. Pending startup, research drafts and simulations never earn stamps; restoration is idempotent. The pilot remains separate from the preserved nine-destination count. Local state is not a server-verified visit attestation or cloud sync.
